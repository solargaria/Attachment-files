## 0. ข้อสังเกตก่อนเริ่ม: ฉบับที่อีฟตรวจอาจไม่ใช่ฉบับล่าสุด

- เมื่อวานนี้ (27 พ.ย. ช่วงบ่าย) รินแก้ WP4 v0.6 สามครั้งในไฟล์ `governance/WP4_v0.6_CR-WP4-002_Applied.md` ใน Project ได้แก่ (1) บรรทัด §3 เพิ่ม "(ระดับ Evidence Item)" (2) แก้หัวเอกสารและส่วนสถานะ (3) แยก Change Log เป็น v0.4→v0.5 และ v0.5→v0.6
- มูนาระบุว่าตรวจไฟล์บน GitHub แล้ว ซึ่งไม่แน่ชัดว่าเป็นฉบับก่อนหรือหลังการแยก Change Log
- **ความเสี่ยง:** มีสองแหล่งที่อาจไม่ตรงกัน (Project และ GitHub) และผลตรวจของอีฟอาจอิงฉบับที่ไม่ใช่ฉบับที่จะเสนอ
- **ต้องยืนยัน:** อีฟตรวจฉบับใด (ระบุ SHA-256 หรือวันเวลาที่บันทึก) และกำหนดว่าแหล่งใดเป็นต้นฉบับที่ใช้อ้างอิง

## 1. Governance Impact: การจัด Change Log ผิดช่วงเวอร์ชัน

**ผลต่อ Traceability**
- Change Log ใช้ระบุว่าการเปลี่ยนแปลงใดเกิดในเวอร์ชันใด การจัดผิดช่วงทำให้ผู้อ่านเข้าใจว่า CR-WP4-002 เป็นส่วนหนึ่งของ v0.5 ซึ่ง Approved แล้ว
- ผลคือ ประวัติการอนุมัติของ v0.5 ถูกอ่านว่ามี CR ที่ยังไม่ได้รับอนุมัติปนอยู่ ทำให้การตรวจย้อนหลังว่า "v0.5 ที่อนุมัติคืออะไร" ไม่ชัด

**ผลต่อการควบคุมเวอร์ชัน**
- GOVERNANCE_RULES §1 กำหนดว่า Active Version คือฉบับล่าสุดที่ Owner อนุมัติ หากเวอร์ชันถูกอ่านผิดช่วง ผู้ใช้อาจอ้างว่า v0.5 มีเนื้อหาของ v0.6 หรือกลับกัน
- VERSION_REGISTER ปัจจุบันระบุ WP4 v0.6 เป็น Hold (CR-WP4-002) ตามเดิม การแยก Change Log ไม่ได้เปลี่ยนสถานะนี้ แต่ต้องตรวจว่าทะเบียนไม่อ้าง Change Log ผิดช่วง

**ข้อค้นพบเพิ่มที่รินตรวจพบ (ไม่ได้อยู่ในผลของอีฟ):**
- หัวเอกสาร "สิ่งที่เปลี่ยนจาก v0.5: เฉพาะ W4-1 ใน §3" ไม่ตรงกับ Change Log v0.5→v0.6 ซึ่งมีรายการ "มติ D-20261127-01" ที่แก้บรรทัด §3 ข้อแรกด้วย การเปลี่ยนนี้ไม่ควรถูกอ้างว่าเป็นส่วนของ W4-1 เพียงอย่างเดียว
- ส่วน "ค่า T_attempt และ T_total: TBD" ขัดกับ WP1 v1.1 ที่ Owner อนุมัติค่าตัวเลือก A (0.5 วินาที / 1.0 วินาที) แล้วเมื่อ 24 พ.ย. 22:03 โดยระบุว่ายังไม่วัดจริง ควรแก้ถ้อยคำให้ตรงกับมติ

## 2. Operational Risk: หาก Owner อนุมัติทั้งที่ Change Log ยังไม่ตรง

| ความเสี่ยง | ผล | ระดับ |
|---|---|---|
| ผู้ใช้เอกสารอ้างผิดเวอร์ชัน | ทีมอ้าง "v0.5 มี CR-WP4-002" หรือตรงกันข้าม ทำให้ตัดสินใจบนฐานที่ไม่ตรง | สูง |
| การตรวจย้อนหลังของ FOUND/RETRIEVAL_FAILED ชี้ไปผิดกฎ | ถ้ากฎ F-7 ถูกอ้างว่ามาจาก v0.5 ที่อนุมัติแล้ว การตรวจจะเชื่อว่าไม่มีการเปลี่ยนเกิดหลังอนุมัติ | สูง |
| Project และ GitHub ไม่ตรงกัน | มีหลายฉบับที่ดูเหมือน "ฉบับจริง" เมื่อเกิดข้อพิพาท | กลาง–สูง |
| Hold ของ WP1 v1.2 และ WP2 v0.2 ถูกมองข้าม | WP4 v0.6 อ้าง CR-WP1 และ CR-WP2 ที่ยังไม่ Approved อาจทำให้ถูกใช้เป็นฐาน | กลาง |
| การอนุมัติถูกตีความเป็นการ Apply/Release | ทะเบียนยังไม่ปรับ แต่ผู้อ่านอาจเชื่อว่าการอนุมัติมีผลเชิงปฏิบัติทันที | กลาง |

**สรุป:** ความเสี่ยงหลักไม่ได้อยู่ที่เนื้อหาข้อกำหนด แต่อยู่ที่ความสามารถในการระบุว่าฉบับไหนคือฐานที่อนุมัติ ซึ่งเป็นเงื่อนไขของการตรวจย้อนหลัง

## 4. Readiness: หลักฐานที่ต้องมีก่อนเสนอ Owner อนุมัติ

เงื่อนไขขั้นต่ำ (ทั้งหมดต้องครบ):

1. **ฉบับที่จะอนุมัติถูกระบุชัด:** SHA-256 ของไฟล์ใน Project หลังแก้ D-1 ถึง D-4 และบันทึกว่า GitHub ตรงกันหรือไม่
2. **ผลตรวจจากอีฟหรือผู้ตรวจอื่นบนฉบับที่ระบุในข้อ 1:** ผ่านเงื่อนไข Structural Review ไม่ใช่ Conditional
3. **Change Log แยกช่วงเวอร์ชันถูกต้อง:** v0.4→v0.5 มีเฉพาะรายการเดิม, v0.5→v0.6 มี CR-WP4-002 และมติ D-20261127-01
4. **หัวเอกสารตรงกับเนื้อหา:** สถานะ, ฉบับก่อนหน้า, การเปลี่ยนแปลงจาก v0.5, ค่า T
5. **Work Log:** รายการ 2026-11-27 มีอยู่แล้ว (ตรวจแล้ว) และระบุการแก้ Change Log ด้วย
6. **DECISION_REGISTER:** คอลัมน์หลักฐานของ D-20261127-01 อัปเดตแล้ว
7. **ไม่มีการแก้เอกสารที่ Approved แล้ว:** WP4 v0.5, WP1 v1.1, WP3 และ WP5 ต้องไม่เปลี่ยนเนื้อหา (ตรวจด้วย SHA-256 เทียบกับประวัติ)
8. **ร่างการเปลี่ยนสถานะที่ Owner จะต้องสั่ง:** VERSION_REGISTER สำหรับ v0.6 Approved และ v0.5 Superseded ต้องอยู่ในรูปข้อเสนอที่ยังไม่ได้ Apply
9. **ข้อความที่ Owner ต้องตัดสิน:** ยืนยันว่า D-1 ถึง D-4 เป็นการแก้ Editorial หรือ Owner ต้องการเห็นการเปลี่ยนแปลงก่อน

**ข้อมูลที่ยังยืนยันไม่ได้ (ต้องตรวจเพิ่ม ไม่คาดเดา):**
- ฉบับที่อีฟตรวจ และ SHA-256 ของฉบับนั้น
- สถานะจริงของไฟล์บน GitHub หลังการแก้ล่าสุด
- ค่า T ที่วัดจริงในระบบ (ยังไม่มี)
